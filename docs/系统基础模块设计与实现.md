## 1. 认证授权模块

### 1.1 模块概述

认证授权模块是校园二手交易平台的安全基石，负责用户身份验证、权限控制和会话管理。该模块采用前后端分离架构，基于JWT（JSON Web Token）实现无状态认证，结合Spring Security构建多层安全防护体系。系统设计了双表隔离的用户体系——普通用户（user_account表）与运营人员（ops_account表）分别存储、分别认证，从数据层面实现了权限隔离。

模块核心设计理念为"无状态、双体系、多层防护"：无状态指JWT令牌自包含用户信息，服务端不维护会话；双体系指普通用户与运营人员使用独立的数据表和认证流程；多层防护指从HTTP请求过滤、JWT验证、Spring Security权限控制到方法级@PreAuthorize注解，形成纵深防御。

### 1.2 业务逻辑分析

#### 1.2.1 用户注册流程

用户注册时需提供用户名、密码、昵称和角色信息。系统对注册请求执行以下业务校验：

1. **用户名唯一性校验**：查询user_account表确认用户名未被占用，若已存在则拒绝注册。
2. **密码强度校验**：要求密码长度不少于6位，防止弱密码。
3. **角色合法性校验**：仅允许BUYER（买家）和SELLER（卖家）两种角色，过滤非法角色值。若未选择角色或角色列表为空，默认分配BUYER角色。
4. **密码加密存储**：使用BCrypt算法对明文密码进行哈希加密后存入数据库，确保即使数据库泄露也无法还原明文密码。
5. **自动登录**：注册成功后自动生成JWT令牌，用户无需再次登录即可进入系统。

#### 1.2.2 用户登录流程

系统支持两种登录入口：普通用户登录和运营人员登录，分别对应不同的认证逻辑。

**普通用户登录**：
1. 根据用户名查询user_account表，若不存在则返回"账号不存在"。
2. 使用BCrypt密码编码器比对输入密码与数据库存储的哈希值，不匹配则返回"密码错误"。
3. 登录成功后，从用户记录中提取id、username、nickname、roles、avatar等字段。
4. 对手机号进行脱敏处理（中间四位替换为****），防止敏感信息泄露。
5. 生成JWT令牌，将username作为subject，userId和roles作为自定义声明写入Token。
6. 返回Token和用户安全信息（不含密码哈希）。

**运营人员登录**：
1. 查询ops_account表验证账号存在性。
2. 额外检查账号状态（status字段），禁用账号（非ACTIVE状态）不允许登录。
3. 密码验证通过后，提取id、username、nickname、roles、roleLevel等运营特有字段。
4. 生成JWT令牌并返回运营人员信息。

#### 1.2.3 密码修改流程

1. 从SecurityContext获取当前认证用户的userId。
2. 查询数据库获取当前密码哈希。
3. 使用BCrypt验证旧密码是否正确。
4. 对新密码进行BCrypt加密后更新到数据库。

#### 1.2.4 登出流程

由于采用JWT无状态认证，服务端不维护Token状态，登出操作仅需前端清除本地存储的Token和用户信息即可。服务端logout方法仅输出日志，无需执行Token失效操作。

#### 1.2.5 权限控制策略

系统采用三层权限控制：

1. **URL级权限**：在SecurityConfig中配置HTTP请求级别的访问控制，公开接口（登录、注册、商品列表GET、圈子GET、字典接口）允许匿名访问，其余接口要求认证。
2. **角色级权限**：路由守卫根据用户角色与路由meta.roles配置进行匹配，角色不匹配则跳转至/forbidden页面。
3. **方法级权限**：使用@PreAuthorize注解对敏感操作（如修改密码、更新资料）进行方法级权限校验。

### 1.3 产品逻辑分析

#### 1.3.1 用户角色体系

系统定义三种核心角色，对应不同的功能权限和使用场景：

| 角色 | 标识 | 可访问区域 | 核心功能 |
|------|------|-----------|---------|
| 买家 | BUYER | /portal/buyer/* | 浏览商品、下单购买、收藏、评价、购物车 |
| 卖家 | SELLER | /portal/seller/* | 发布商品、管理商品、查看订单、查看统计 |
| 运营 | OPS | /ops/* | 商品审核、用户管理、订单管理、数据统计 |

用户注册时可同时选择BUYER和SELLER角色，实现买卖双重身份。运营人员通过独立的ops_account表管理，与普通用户完全隔离。

#### 1.3.2 Token生命周期管理

- **Token生成**：登录或注册成功时由后端JwtUtil生成，默认有效期24小时（86400000毫秒）。
- **Token存储**：前端将Token存储在localStorage中，键名为campus_market_token（普通用户）或campus_ops_token（运营人员）。
- **Token传递**：每次API请求通过Axios请求拦截器自动在Authorization头注入Bearer Token。
- **Token验证**：后端JwtAuthenticationFilter在每个请求中提取并验证Token，解析出用户信息设置到SecurityContext。
- **Token过期处理**：前端通过jwt.js工具类检测Token过期状态，响应拦截器捕获401状态码后自动清除Token并跳转登录页。

#### 1.3.3 路由权限守卫

前端路由守卫在每次路由跳转前执行以下检查：

1. **状态恢复**：若Store中无用户信息且存在Token，调用hydrate()从localStorage恢复状态。
2. **登录检查**：未登录用户访问需认证路由时，重定向至登录页，并携带原始路径作为redirect参数，登录后自动跳回。
3. **白名单放行**：/login和/forbidden路径无需认证，直接放行。
4. **角色匹配**：使用hasAnyRole函数检查用户角色是否满足路由meta.roles要求，不满足则跳转/forbidden页面。

### 1.4 技术实现分析

#### 1.4.1 后端实现

**Controller层 — AuthController**

AuthController是认证授权的入口控制器，映射路径为/api/auth，提供8个HTTP端点：

```java
@RestController
@RequestMapping("/api/auth")
@Validated
public class AuthController {
    @PostMapping("/login")        // 用户登录
    @PostMapping("/register")     // 用户注册
    @PostMapping("/logout")       // 用户登出
    @PostMapping("/ops/login")    // 运营登录
    @PostMapping("/ops/logout")   // 运营登出
    @GetMapping("/current")       // 获取当前用户
    @GetMapping("/ops/current")   // 获取当前运营用户
    @PutMapping("/profile")       // 更新资料
    @PutMapping("/avatar")        // 更新头像
    @PutMapping("/password")      // 修改密码
}
```

Controller使用Java Record定义请求体结构，结合@NotBlank和@Validated注解实现声明式参数校验。密码修改接口使用@PreAuthorize("isAuthenticated()")确保仅认证用户可访问。

**Service层 — AuthService / OpsAuthService**

AuthService负责普通用户的认证业务逻辑，核心方法包括：

- `login(username, password)`：执行用户名查询、密码验证、Token生成、敏感信息脱敏。
- `register(username, password, nickname, roles)`：执行参数校验、角色过滤、用户创建、自动登录。
- `getCurrentUser(userId)`：根据userId查询用户信息。
- `logout()`：无状态登出，仅输出日志。

OpsAuthService负责运营人员的认证逻辑，与AuthService类似但增加了账号状态检查（status必须为ACTIVE），并从ops_account表查询数据。其isOpsLogin()方法通过检查SecurityContext中Authentication的authorities是否包含"OPS"前缀来判断当前是否为运营人员登录。

**CurrentUserService**

CurrentUserService是一个通用服务，封装了从SecurityContext获取当前用户信息的逻辑：

- `userId()`：优先从Authentication.details中获取userId（由JwtAuthenticationFilter设置），备选方案通过username查询数据库。
- `currentUser()`：返回当前用户的完整信息Map。
- `roles()`：返回当前用户的角色列表。

**安全配置 — SecurityConfig**

SecurityConfig是Spring Security的核心配置类，定义了整个应用的安全策略：

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
public class SecurityConfig {
    // CSRF禁用（前后端分离架构使用Token认证）
    // CORS配置：允许所有来源、所有Header、所有方法
    // 会话管理：STATELESS无状态模式
    // 公开接口：登录/注册/商品GET/圈子GET/字典接口
    // 其余接口：需认证
    // JWT过滤器：添加在UsernamePasswordAuthenticationFilter之前
    // 密码编码器：BCryptPasswordEncoder
}
```

关键设计决策：
- CSRF保护禁用：前后端分离架构下，JWT通过Authorization头传递，不依赖Cookie，CSRF攻击风险极低。
- CORS全开放：开发阶段允许所有来源，生产环境应限制为前端域名。
- 无状态会话：Spring Security不创建HttpSession，完全依赖JWT进行认证。

**JWT过滤器 — JwtAuthenticationFilter**

JwtAuthenticationFilter继承OncePerRequestFilter，确保每个HTTP请求仅执行一次JWT验证：

1. 从请求头Authorization中提取Bearer Token。
2. 调用JwtUtil.validateToken()验证Token签名和有效期。
3. 解析Token提取username、userId、roles。
4. 将roles转换为Spring Security的SimpleGrantedAuthority列表（添加"ROLE_"前缀）。
5. 构建UsernamePasswordAuthenticationToken并设置details为userId。
6. 将Authentication对象设置到SecurityContextHolder。

**JWT工具类 — JwtUtil**

JwtUtil封装了JWT的生成、解析和验证逻辑，基于JJWT 0.12.6库实现：

- 签名算法：HMAC-SHA（通过Keys.hmacShaKeyFor生成密钥）
- Token结构：Header（算法类型）.Payload（subject=username, claims={userId, roles}, issuedAt, expiration）.Signature
- 密钥来源：配置项jwt.secret，默认值为长度足够的字符串以满足HMAC-SHA256的密钥长度要求
- 过期时间：配置项jwt.expiration，默认86400000毫秒（24小时）

**Repository层 — UserRepository / OpsAccountRepository**

UserRepository使用JdbcTemplate实现用户数据的CRUD操作，核心方法包括：

- `findByUsername(username)`：按用户名查询，返回Optional<Map<String, Object>>
- `findById(id)`：按ID查询
- `create(username, password, nickname, roles)`：创建用户，roles以逗号分隔字符串存储
- `updateProfile(userId, nickname, email, bio, campus, phone)`：动态SQL更新用户资料
- `updateAvatar(userId, avatarUrl)`：更新头像URL
- `updatePassword(userId, newPassword)`：更新密码哈希
- `countByDateRange(startTime, endTime)`：按日期范围统计用户数
- `countActiveUsers()`：统计30天内活跃用户（通过item和orders表的更新时间联合查询）
- `countByRole(role)`：按角色统计用户数（使用LIKE模糊匹配）
- `findByPage(keyword, pageNo, pageSize)`：分页查询，支持按用户名或昵称搜索

OpsAccountRepository使用独立的RowMapper将结果映射为OpsAccount内部类对象，包含id、username、password、nickname、roles、roleLevel、status字段，并提供getRolesList()方法将逗号分隔的roles字符串转换为List。

#### 1.4.2 前端实现

**状态管理 — Pinia auth store**

auth store使用Pinia定义，管理全局认证状态：

```javascript
state: {
    token: "",        // JWT令牌
    user: null,       // 用户信息对象
}
getters: {
    roles,            // 从JWT解析角色，备选从user.roles获取
    isLoggedIn,       // Boolean(token)判断
    isJWTToken,       // 检测Token是否为JWT格式
    isTokenExpired,   // 检测JWT是否已过期
}
actions: {
    hydrate(),        // 从localStorage恢复状态，支持JWT自包含恢复
    login(payload),   // 调用登录API，保存Token和用户信息
    register(payload),// 调用注册API
    logout(),         // 清除Token和用户信息
}
```

hydrate()方法实现了智能状态恢复：优先从localStorage读取Token和用户信息，若用户信息为空但Token为有效JWT，则从Token的Payload中解析出用户信息进行恢复。

**JWT工具类 — jwt.js**

jwt.js提供纯前端JWT解析和验证功能，不依赖任何后端接口：

- `isJWT(token)`：检测字符串是否为三段式JWT格式
- `parseJWT(token)`：Base64解码Payload部分，返回JSON对象
- `isJWTExpired(token)`：比较exp声明与当前时间
- `getJWTRoles(token)`：从Payload中提取roles数组，兼容字符串和对象格式
- `getJWTUserInfo(token)`：从Payload中提取完整用户信息
- `formatJWTToken(token)`：确保Token带有"Bearer "前缀
- `validateJWT(token)`：综合验证Token格式、有效期和用户信息完整性

**路由守卫 — router/index.js**

路由守卫通过Vue Router的beforeEach钩子实现：

```javascript
router.beforeEach(async (to) => {
    // 1. 状态恢复
    if (!authStore.user && !authStore.token) {
        authStore.hydrate();
    }
    // 2. 未登录检查
    if (!authStore.isLoggedIn) {
        if (whiteList.includes(to.path)) return true;
        if (requiresAuth) return { name: "login", query: { redirect: to.fullPath } };
        return true;
    }
    // 3. 角色匹配检查
    if (to.meta.roles && !hasAnyRole(userRoles, requiredRoles)) {
        return { name: "forbidden" };
    }
    return true;
});
```

路由元信息meta.roles定义了各路由所需的角色，如买家中心路由要求BUYER角色，运营后台路由要求OPS角色。

**HTTP拦截器 — http.js**

Axios实例配置了请求和响应两个拦截器：

- **请求拦截器**：从localStorage读取Token，若为JWT格式则使用formatJWTToken()格式化后注入Authorization头；同时检测Token是否即将过期并输出警告。
- **响应拦截器**：捕获401状态码响应，自动清除localStorage中的Token和用户信息，跳转至登录页。

### 1.7 关键代码实现说明

**BCrypt密码加密**：AuthService中直接实例化BCryptPasswordEncoder，调用matches()方法验证密码、encode()方法加密密码。BCrypt自动生成随机盐值并嵌入哈希结果，每次加密同一明文产生不同哈希值，有效防止彩虹表攻击。

**JWT Token自包含设计**：Token的Payload中包含userId和roles两个自定义声明，前端可直接从Token解析出用户角色，无需额外请求后端接口。这种设计减少了网络请求次数，但需注意Token一旦签发无法撤销（除非过期），因此Token有效期不宜过长。

**SecurityContext用户ID传递**：JwtAuthenticationFilter将userId设置到Authentication.details字段，CurrentUserService优先从details获取userId，避免每次请求都查询数据库。备选方案通过username查询数据库获取userId，确保在details丢失时仍能正常工作。

**前端Token双重存储**：用户信息同时存储在localStorage（持久化）和Pinia Store（响应式）中。hydrate()方法在页面刷新时从localStorage恢复状态到Store，确保刷新后认证状态不丢失。

## 2. 文件上传模块

### 2.1 模块概述

文件上传模块为平台提供统一的图片上传和存储能力，主要服务于商品发布（商品图片）、用户头像上传和富文本编辑器图片插入三个场景。模块采用Base64编码存储策略，将图片数据直接写入数据库的LONGTEXT字段，简化了文件系统管理，适合校园交易平台的中小规模图片存储需求。

### 2.2 业务逻辑分析

1. **文件类型限制**：仅允许上传JPG、PNG、GIF、WebP、BMP五种图片格式，前后端双重校验。
2. **文件大小限制**：单文件不超过5MB，防止大文件占用过多存储空间。
3. **文件命名策略**：使用UUID生成唯一存储文件名，避免文件名冲突和路径遍历攻击。
4. **存储策略**：图片以Base64编码存入数据库，同时生成Data URL（data:mime;base64,data）作为访问地址，无需额外的文件服务器。
5. **权限控制**：上传接口要求用户已认证（@PreAuthorize("isAuthenticated()")），并记录上传者ID。

### 2.3 产品逻辑分析

- **商品发布场景**：ImageUploader组件支持配置limit属性控制最大上传数量，单图模式返回字符串URL，多图模式返回URL数组。
- **头像上传场景**：单图上传，上传成功后调用PUT /api/auth/avatar接口更新用户头像。
- **富文本编辑器场景**：RichEditor组件集成图片上传功能，通过隐藏的file input触发文件选择，上传成功后将图片插入编辑器内容。

### 2.4 技术实现分析

#### 2.4.1 后端实现

**UploadController**

```java
@RestController
@RequestMapping("/api")
@PreAuthorize("isAuthenticated()")
public class UploadController {
    @PostMapping(value = "/upload", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public Map<String, Object> upload(@RequestParam("file") MultipartFile file) {
        Long uploaderId = currentUserService.userId();
        Map<String, Object> result = uploadService.upload(file, uploaderId);
        return Map.of("code", 200, "data", result);
    }
}
```

控制器使用consumes = MediaType.MULTIPART_FORM_DATA_VALUE确保仅接受multipart/form-data请求，@PreAuthorize注解要求用户已认证。

**UploadService**

UploadService实现文件上传的核心业务逻辑：

1. 空文件校验：检查file是否为null或isEmpty。
2. 大小校验：file.getSize()与MAX_FILE_SIZE(5MB)比较。
3. 类型校验：contentType与ALLOWED_CONTENT_TYPES集合匹配。
4. 文件读取：调用file.getBytes()获取字节数组。
5. Base64编码：使用java.util.Base64编码字节数组。
6. 生成Data URL：格式为data:{contentType};base64,{base64Data}。
7. 生成存储文件名：UUID + 原始文件扩展名。
8. 持久化：调用UploadRepository.save()写入数据库。
9. 返回结果：包含url(Data URL)、originalName、fileSize、id。

**UploadRepository**

使用JdbcTemplate和GeneratedKeyHolder实现数据持久化，INSERT语句使用PreparedStatement.RETURN_GENERATED_KEYS获取自增主键。

#### 2.4.2 前端实现

**ImageUploader组件**

ImageUploader是基于Arco Design Vue的a-upload组件封装的图片上传组件：

- 上传成功后从响应中提取url，更新modelValue。

**RichEditor组件**

- 使用@tiptap/vue-3、@tiptap/starter-kit、@tiptap/extension-image、@tiptap/extension-link、@tiptap/extension-placeholder五个扩展。
- 工具栏提供加粗、斜体、删除线、列表、标题、图片、链接等格式化操作。
- 图片上传通过隐藏的file input触发，上传成功后调用editor.chain().focus().setImage({src: url}).run()插入图片。

## 4. 通知消息模块

### 4.1 模块概述

通知消息模块为平台提供站内消息通知能力，支持系统公告、交易通知、审核通知和互动通知四种消息类型。模块采用经典的分层架构（Controller → Service → Repository），使用实体（Entity）和数据传输对象（DTO）分离设计，支持消息的发送、查询、已读标记和删除等完整生命周期管理。

### 4.2 业务逻辑分析

#### 4.2.1 消息类型体系

| 类型 | 标识 | 图标 | 颜色 | 场景 |
|------|------|------|------|------|
| 系统通知 | SYSTEM | InfoCircle | 蓝色(#165DFF) | 平台公告、维护通知、功能上线 |
| 交易通知 | TRANSACTION | Apps | 橙色(#FF7D00) | 订单状态变更、发货通知、退款通知 |
| 审核通知 | REVIEW | CheckCircle | 绿色(#00B42A) | 商品审核结果、评价审核结果 |
| 互动通知 | INTERACTION | HeartFill | 红色(#F53F3F) | 评论通知、点赞通知、关注通知 |

#### 4.2.2 消息优先级

| 优先级 | 标识 | 颜色 | 说明 |
|--------|------|------|------|
| 低 | LOW | 灰色 | 一般性通知 |
| 中 | MEDIUM | 蓝色 | 默认优先级 |
| 高 | HIGH | 橙色 | 需要及时处理的通知 |
| 紧急 | URGENT | 红色 | 需要立即处理的通知 |

#### 4.2.3 消息状态流转

消息从创建到删除经历以下状态：

1. **创建**：消息被创建时，status=ACTIVE，is_read=false，deleted=0。
2. **已读**：用户标记消息已读，is_read=true，read_at=当前时间。
3. **删除**：用户删除消息，执行软删除，status=DELETED，deleted标记不变（通过status字段区分）。

#### 4.2.4 业务通知自动生成

NotificationService提供createBusinessNotification()方法，供其他业务模块在特定事件发生时自动生成通知：

- 商品审核通过/驳回时，向卖家发送审核结果通知。
- 订单状态变更时，向买家/卖家发送交易通知。
- 用户被禁用/解禁时，发送系统通知。

### 4.3 产品逻辑分析

- **Header未读角标**：页面顶部导航栏显示未读消息数量角标（最大显示99+），吸引用户关注。
- **MessageCenter下拉面板**：点击消息图标弹出下拉面板，显示最近5条消息，支持全部标记已读和查看全部跳转。
- **MessageList完整页面**：独立的消息中心页面，支持按类型筛选、分页浏览、批量标记已读、批量删除等操作。
- **消息点击跳转**：点击消息可跳转到关联的业务页面（如订单详情、商品详情等）。

#### 4.4.1 后端实现

## 5. 地址管理模块

### 5.1 模块概述

地址管理模块为平台提供收货地址的增删改查功能，支持多地址管理和默认地址设置。模块采用标准的RESTful API设计，前端提供卡片式地址列表和模态框编辑表单，后端通过userId实现用户级数据隔离，确保用户只能操作自己的地址数据。

### 5.2 业务逻辑分析

1. **地址创建**：用户首次创建地址时自动设为默认地址（addressCount == 0时强制isDefault=true），后续创建的地址根据用户选择决定是否设为默认。
2. **默认地址设置**：设置默认地址采用"先清后设"策略——先将该用户所有地址的is_default设为false，再将目标地址的is_default设为true，确保每个用户只有一个默认地址。
3. **地址更新**：更新时验证地址归属权（userId匹配），若isDefault为true则同步执行默认地址设置逻辑。
4. **地址删除**：删除时验证地址归属权，使用物理删除（DELETE语句）。
5. **默认地址查询**：优先查询is_default=true的地址，若无默认地址则返回第一条地址记录。

### 5.3 产品逻辑分析

- **地址列表页面**：以卡片网格布局展示用户所有地址，默认地址排在最前（ORDER BY is_default DESC, created_at DESC），带有紫色渐变徽章标识。
- **地址编辑弹窗**：使用Arco Design的a-modal组件，表单包含收货人、联系电话、省市区级联选择、详细地址、邮政编码、默认地址开关。
- **省市区级联选择**：使用a-cascader组件，内置北京、上海、广东、浙江、江苏等省市的区县数据。
- **手机号脱敏**：地址列表中手机号中间四位显示为****。
- **删除确认**：使用a-popconfirm组件进行二次确认，防止误删。

### 5.4 技术实现分析

#### 5.4.1 后端实现

**AddressController**

```java
@RestController
@RequestMapping("/api/addresses")
@Validated
public class AddressController {
    @GetMapping              // 获取地址列表
    @GetMapping("/default")  // 获取默认地址
    @GetMapping("/{id}")     // 获取单个地址
    @PostMapping             // 创建地址
    @PutMapping("/{id}")     // 更新地址
    @DeleteMapping("/{id}")  // 删除地址
    @PutMapping("/{id}/default") // 设置默认地址
}
```

使用Java Record定义AddressRequest请求体，@NotBlank注解校验必填字段（receiverName、receiverPhone、province、city、detailAddress）。

**AddressService**

AddressService封装地址业务逻辑，核心特点：

- 所有操作均通过currentUserService.userId()获取当前用户ID，实现用户级数据隔离。
- 创建和更新操作均执行参数校验（非空检查），确保数据完整性。
- 查询和修改操作均验证地址归属权，防止越权访问。
- 创建地址时自动处理默认地址逻辑：首个地址强制为默认，后续地址根据参数决定。

**AddressRepository**

使用JdbcTemplate实现数据访问，核心方法：

- `create()`：使用GeneratedKeyHolder获取自增主键。
- `findByUserId()`：按用户ID查询，按默认地址优先、创建时间倒序排列。
- `findDefaultByUserId()`：查询用户的默认地址。
- `setDefault()`：两步操作——先清除所有默认标记，再设置指定地址为默认。
- `countByUserId()`：统计用户地址数量，用于首次地址自动默认逻辑。

#### 5.4.2 前端实现

**AddressList页面**

完整的地址管理页面，功能包括：

## 6. UI设计规范系统

### 6.1 模块概述

UI设计规范系统是校园二手交易平台的视觉基础设施，定义了色彩、字体、间距、圆角、阴影等设计Token，以及运营后台的完整主题变量体系。该系统采用SCSS变量 + CSS自定义属性（CSS Variables）双轨制，SCSS变量用于编译时样式计算，CSS变量用于运行时主题切换，确保设计一致性和可维护性。

### 6.2 业务逻辑分析

UI设计规范系统虽不直接承载业务逻辑，但通过规范化的设计Token确保了以下业务目标的实现：

1. **品牌一致性**：主色调#165DFF贯穿所有页面，建立统一的品牌视觉识别。
2. **信息层级清晰**：通过6级灰阶和4级字重建立文本信息层级，帮助用户快速识别重要信息。
3. **状态反馈明确**：功能色（成功/警告/危险/信息）与业务状态一一对应，用户无需阅读文字即可感知状态。
4. **运营后台差异化**：深色侧边栏主题与门户白色主题形成视觉区分，降低用户混淆风险。

### 6.3 产品逻辑分析

#### 6.3.1 门户端设计语言

门户端面向普通用户（买家和卖家），采用明亮的白色基调设计：

- **页面背景**：#F5F6F7浅灰色，与白色卡片形成层次感。
- **卡片容器**：白色背景(#FFFFFF) + 轻阴影，营造悬浮感。
- **主色调**：#165DFF蓝色，用于按钮、链接、选中态等强调元素。
- **圆角风格**：中等圆角(8px-12px)，现代感与亲和力兼顾。

#### 6.3.2 运营后台设计语言

运营后台面向管理人员，采用深蓝白色调设计：

- **侧边栏**：深色背景(#0D1626/#1A2332)，与内容区形成强对比。
- **内容区**：白色背景，与门户端保持一致。
- **工具栏**：渐变背景(#f0f5ff → #fff)，视觉引导操作区域。
- **状态标签**：通过Mixin快速生成统一的状态标签样式。

### 7.2 模块协作详解

#### 7.2.1 认证授权模块 → 其他所有模块

认证授权模块是所有业务模块的基础依赖，提供以下协作能力：

- **CurrentUserService**：所有需要获取当前用户ID的Controller（UploadController、AddressController等）均依赖此服务。
- **JwtAuthenticationFilter**：所有需要认证的API请求均经过此过滤器验证。
- **SecurityConfig**：定义了各模块API的访问权限规则（公开/认证）。
- **Pinia auth store**：前端所有需要判断登录状态和用户角色的页面均依赖此Store。
- **Axios拦截器**：所有HTTP请求自动注入Token，所有401响应自动处理。

具体依赖关系：

| 依赖模块 | 依赖方式 | 说明 |
|---------|---------|------|
| 文件上传 | @PreAuthorize("isAuthenticated()") + currentUserService.userId() | 上传文件需认证，记录上传者 |
| 地址管理 | currentUserService.userId() | 所有地址操作基于当前用户ID |
| 通知消息 | SecurityContext获取当前用户 | 消息按用户隔离查询 |
| 数据字典 | SecurityConfig中配置公开访问 | 字典接口无需认证 |

#### 7.2.2 文件上传模块 → 业务模块

文件上传模块被以下业务场景调用：

- **商品发布**：ImageUploader组件上传商品图片，返回的Data URL存入item表的image_urls字段。
- **用户头像**：上传头像后调用AuthController.updateAvatar()更新user_account表的avatar字段。
- **富文本编辑**：RichEditor组件上传图片插入编辑内容，用于圈子帖子等场景。

#### 7.2.3 数据字典模块 → 业务模块

数据字典模块为以下场景提供选项数据：

- **运营后台**：用户管理页面的角色筛选器、状态筛选器使用getUserRoles()和getUserStatuses()。
- **商品管理**：商品状态筛选使用getItemStatuses()，分类筛选使用categories数据。
- **订单管理**：订单状态筛选使用getOrderStatuses()。
- **评价管理**：评价审核状态筛选使用getReviewModerationStatuses()，评价类型筛选使用getReviewTypes()。
- **门户前端**：商品分类选择、成色选择使用constants.js中的CATEGORIES和ITEM_CONDITION静态常量。

#### 7.2.4 通知消息模块 → 业务模块

通知消息模块被以下业务事件触发：

- **商品审核**：审核通过/驳回时调用createBusinessNotification()向卖家发送通知。
- **订单状态变更**：订单发货、完成等状态变更时向买家/卖家发送交易通知。
- **用户管理**：用户被禁用/解禁时发送系统通知。
- **评价审核**：评价审核结果通知。

#### 7.2.5 地址管理模块 → 订单模块

地址管理模块为订单模块提供收货地址数据：

- **订单创建**：下单时从地址列表选择收货地址，地址信息（receiverName、receiverPhone、receiverAddress）写入orders表。
- **订单确认页**：OrderConfirm页面调用getDefaultAddress()获取默认地址，提供快捷选择。

#### 7.2.6 UI设计规范系统 → 所有前端模块

UI设计规范系统为所有前端页面和组件提供视觉基础：

- **SCSS变量**：所有.vue文件的`<style lang="scss">`块可直接引用_variables.scss、_spacing.scss等文件中定义的变量。
- **CSS变量**：运营后台页面通过var(--ops-*)引用主题变量，支持运行时主题切换。
- **Mixin**：运营后台组件使用ops-card、ops-toolbar等Mixin快速生成统一样式。
- **theme.js**：ArcoConfigProvider组件使用theme配置对象定制组件库主题。
- **响应式断点**：所有页面使用respond-to Mixin实现移动端适配。

### 7.5 跨模块调用链路示例

**商品发布完整调用链路**：

```
1. 用户点击"发布商品"
2. 路由守卫检查SELLER角色权限
3. PublishItem页面加载
4. ImageUploader组件上传图片
   → POST /api/upload（需认证）
   → JwtAuthenticationFilter验证Token
   → CurrentUserService获取userId
   → UploadService.upload()
   → UploadRepository.save()
5. 用户填写商品信息，选择分类和成色
   → 分类数据来自constants.js的CATEGORIES
   → 成色数据来自constants.js的ITEM_CONDITION
6. 提交商品
   → POST /api/items（需认证）
   → 商品审核通过后触发通知
   → NotificationService.createBusinessNotification()
```

**订单创建中的地址选择链路**：

```
1. 用户点击"确认订单"
2. OrderConfirm页面加载
3. 调用GET /api/addresses/default获取默认地址
   → AddressService.getDefaultAddress()
   → AddressRepository.findDefaultByUserId()
4. 用户切换地址
   → 调用GET /api/addresses获取地址列表
   → AddressService.getAddressList()
5. 提交订单，地址信息写入orders表
```
