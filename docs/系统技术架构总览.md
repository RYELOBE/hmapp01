# 系统技术架构总览

## 1 系统整体技术架构

### 1.1 前后端分离架构设计

本系统采用前后端分离的架构模式，前端与后端各自独立开发、独立部署、独立演进，通过RESTful API进行数据交互。该架构模式的核心优势在于：前后端团队可并行开发，互不阻塞；前端SPA应用提供流畅的用户体验，后端REST API保持无状态特性，便于水平扩展。

```
┌─────────────────────────────────────────────────────────────────────┐
│                          客户端层（Browser）                         │
│                                                                     │
│  ┌──────────────────────────┐    ┌──────────────────────────────┐  │
│  │    门户端（Portal SPA）    │    │   运营后台（Ops SPA）          │  │
│  │    Vue 3 + Arco Design   │    │   Vue 3 + Arco Design Pro    │  │
│  └────────────┬─────────────┘    └──────────────┬───────────────┘  │
│               │                                  │                  │
│               └──────────────┬───────────────────┘                  │
│                              │ Axios HTTP Client                    │
│                              │ Authorization: Bearer <JWT>         │

│  └─────────────┘  └──────────────┘  └──────────────┬─────────────┘ │
```

**架构分层说明：**

| 层次 | 技术选型 | 职责 |
|------|---------|------|
| 客户端层 | Vue 3 SPA + Arco Design | 用户交互、页面渲染、状态管理、路由控制 |
| 网关层 | Nginx | 反向代理、静态资源托管、SSL终止、负载均衡 |
| 服务层 | Spring Boot 3.3.5 | 业务逻辑处理、API接口暴露、安全认证、数据组装 |
| 持久层 | MySQL 8.x + JdbcTemplate | 数据持久化存储、事务管理、索引优化 |

### 1.2 RESTful API设计原则

本系统严格遵循RESTful架构风格，以资源为核心组织API，保证接口的语义化、一致性和可维护性。

**资源化URL设计：**

API路径以资源名词为核心，采用复数形式表示资源集合，通过路径参数定位具体资源实例：

```
GET    /api/items          # 获取商品列表
GET    /api/items/{id}     # 获取单个商品详情
POST   /api/items          # 创建商品
PUT    /api/items/{id}     # 更新商品信息
DELETE /api/items/{id}     # 删除商品

GET    /api/orders         # 获取订单列表
POST   /api/orders         # 创建订单
PATCH  /api/orders/{id}    # 部分更新订单状态

GET    /api/users/me       # 获取当前用户信息
```

**HTTP方法语义化：**

| HTTP方法 | 语义 | 幂等性 | 安全性 | 典型场景 |
|---------|------|--------|--------|---------|
| GET | 获取资源 | 是 | 是 | 查询商品、获取订单 |
| POST | 创建资源 | 否 | 否 | 发布商品、下单 |
| PUT | 全量更新资源 | 是 | 否 | 修改商品信息 |
| PATCH | 部分更新资源 | 否 | 否 | 更新订单状态 |
| DELETE | 删除资源 | 是 | 否 | 删除收藏、下架商品 |

**统一响应格式：**

所有API接口均返回统一的JSON响应结构，便于前端统一处理：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { ... }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| code | Integer | 业务状态码，200表示成功，4xx表示客户端错误，5xx表示服务端错误 |
| message | String | 响应描述信息，成功时返回操作提示，失败时返回错误原因 |
| data | Object | 业务数据载体，成功时携带具体数据，失败时可为null |

### 1.3 JWT无状态认证架构

本系统采用JWT（JSON Web Token）作为认证方案，实现无状态的身份验证机制，避免传统Session方案在分布式环境下的共享问题，天然支持服务的水平扩展。

**JWT认证架构流程：**

```
┌────────┐     ①登录请求      ┌────────────┐    ②验证密码     ┌──────────┐
│        │ ──────────────────→ │            │ ──────────────→ │          │
│  前端   │                    │ Controller │                 │ Service  │
│        │ ←────────────────── │            │ ←────────────── │          │
└────────┘     ③返回JWT       └────────────┘    ④生成Token    └──────────┘
     │                                              │
     │  ⑤存储Token至localStorage                    │
     │                                              │
     │  ⑥后续请求携带Authorization: Bearer <JWT>     │
     ▼                                              ▼
┌────────┐     请求+Token      ┌──────────────────┐
│        │ ──────────────────→ │ JwtAuthentication│
│  前端   │                    │ Filter           │
│        │ ←────────────────── │ ⑦解析验证Token    │
└────────┘     响应数据        │ ⑧设置SecurityCtx │
                               └──────────────────┘
```

**JWT Token结构：**

Token由三部分组成：Header（算法与类型）、Payload（业务声明）、Signature（签名防篡改）。

Payload中包含以下核心声明（Claims）：

| 声明字段 | 说明 | 示例 |
|---------|------|------|
| sub | 主题，即用户名 | "zhangsan" |
| userId | 用户唯一标识 | 10001 |
| roles | 用户角色列表 | ["BUYER","SELLER"] |
| iat | 签发时间 | 1700000000 |
| exp | 过期时间（24小时） | 1700086400 |

**无状态认证的优势：**

1. **水平扩展友好**：服务端无需存储Session，任意实例均可验证Token，无需Session同步
2. **跨域支持**：Token通过HTTP Header传递，天然支持CORS场景
3. **移动端适配**：无Cookie依赖，移动端原生应用可无缝接入
4. **性能优化**：避免Session存储的内存开销和Redis查询延迟

### 1.4 RBAC角色权限体系

本系统实现了基于角色的访问控制（Role-Based Access Control），定义了三种核心角色，并在路由级、接口级、方法级三个层次实现权限控制。

**角色定义：**

| 角色 | 标识 | 说明 | 典型权限 |
|------|------|------|---------|
| 买家 | BUYER | 普通消费者角色 | 浏览商品、下单购买、收藏、评价 |
| 卖家 | SELLER | 商品发布者角色 | 发布商品、管理库存、处理订单 |
| 运营 | OPS | 平台运营管理员 | 商品审核、用户管理、数据统计 |

**三层权限控制体系：**

```
┌─────────────────────────────────────────────────────────┐
│                    第一层：路由级权限                       │
│  Vue Router meta.roles 定义页面访问权限                    │
│  beforeEach 全局守卫校验用户角色是否匹配                    │
│  不匹配则重定向至403页面或首页                              │
├─────────────────────────────────────────────────────────┤
│                    第二层：接口级权限                       │
│  Spring Security SecurityFilterChain 配置                │
│  URL模式匹配 + 角色要求 (permitAll / authenticated)       │
│  请求到达Controller前完成接口级鉴权                        │
├─────────────────────────────────────────────────────────┤
│                    第三层：方法级权限                       │
│  @PreAuthorize 注解在Service方法上声明细粒度权限            │
│  支持SpEL表达式实现复杂权限逻辑                            │
│  @EnableMethodSecurity 启用方法级安全                     │
└─────────────────────────────────────────────────────────┘
```

**路由级权限实现：**

前端通过Vue Router的路由元信息（meta）声明每个路由所需的角色：

```javascript
{
  path: '/ops/dashboard',
  component: () => import('@/views/ops/Dashboard.vue'),
  meta: { roles: ['OPS'] }
}
```

全局路由守卫在每次导航前校验用户角色：

```javascript
router.beforeEach((to, from, next) => {
  const authStore = useAuthStore()
  if (to.meta.roles && !to.meta.roles.some(role => authStore.roles.includes(role))) {
    next('/403')
  } else {
    next()
  }
})
```

### 1.5 运营系统与用户系统双轨隔离

本系统在架构层面实现了运营系统与用户系统的双轨隔离，确保两套体系在登录入口、数据存储、Token管理三个维度完全独立，避免权限交叉和数据泄露。

**双轨隔离架构：**

```
┌──────────────────────────────────────────────────────────────┐
│                        前端双入口                              │
│                                                              │
│  ┌───────────────────────┐    ┌────────────────────────────┐ │
│  │   门户端 /login        │    │   运营后台 /ops/login       │ │
│  │   用户登录入口          │    │   运营人员登录入口           │ │
│  │   Token → user_token   │    │   Token → ops_token        │ │
│  └───────────┬───────────┘    └─────────────┬──────────────┘ │
└──────────────┼──────────────────────────────┼────────────────┘
               │                              │
               ▼                              ▼
┌──────────────────────────────────────────────────────────────┐
│                        后端双体系                              │
│                                                              │
│  ┌───────────────────────┐    ┌────────────────────────────┐ │
│  │  user_account 表       │    │  ops_account 表            │ │
│  │  用户账号数据           │    │  运营账号数据               │ │
│  │  独立密码、独立角色      │    │  独立密码、独立权限          │ │
│  └───────────────────────┘    └────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**隔离维度详解：**

| 隔离维度 | 门户端（用户系统） | 运营后台（运营系统） |
|---------|------------------|-------------------|
| 登录入口 | `/login` | `/ops/login` |
| 数据表 | `user_account` | `ops_account` |
| Token存储键 | `user_token` | `ops_token` |
| 角色体系 | BUYER / SELLER | OPS |
| 前端Layout | PortalLayout | OpsLayout |
| API前缀 | `/api/` | `/api/ops/` |

双轨隔离的设计确保了：运营人员无法以用户身份操作交易流程，普通用户无法访问运营管理功能，即使Token被窃取，攻击者也无法跨体系使用，因为两套Token的生成上下文和验证逻辑完全独立。

## 2 前端技术栈详解

### 2.1 Vue 3.5.x

Vue 3是本系统前端框架的核心，采用Composition API配合`<script setup>`语法糖，实现更简洁、更高效的组件开发模式。

**Composition API + script setup：**

`<script setup>`是Vue 3.2+引入的编译时语法糖，相比传统的Options API，具有以下优势：

- **更少的样板代码**：无需`data()`、`methods`、`computed`等选项声明，变量和函数直接在`<script setup>`中定义即可自动暴露给模板
- **更好的TypeScript支持**：基于变量的类型推导更加自然
- **更灵活的逻辑复用**：通过组合式函数（Composables）实现逻辑的提取与复用，替代Mixins的命名冲突问题

```vue
<script setup>
import { ref, computed, onMounted } from 'vue'
import { useAuthStore } from '@/stores/auth'

const authStore = useAuthStore()
const items = ref([])
const keyword = ref('')

const filteredItems = computed(() =>
  items.value.filter(item => item.title.includes(keyword.value))
)

onMounted(async () => {
  items.value = await fetchItems()
})
</script>
```

**响应式系统：**

Vue 3的响应式系统基于ES6 Proxy实现，提供了两种响应式API：

| API | 适用场景 | 特点 |
|-----|---------|------|
| `ref()` | 基本类型值（字符串、数字、布尔值） | 通过`.value`访问，模板中自动解包 |
| `reactive()` | 对象类型值（对象、数组） | 直接访问属性，无需`.value` |
| `computed()` | 派生状态 | 具有缓存性，依赖不变时不会重新计算 |

**生命周期钩子：**

| 钩子函数 | 对应Options API | 说明 |
|---------|----------------|------|
| `onMounted()` | `mounted` | DOM挂载完成后调用，常用于发起初始数据请求 |
| `onUpdated()` | `updated` | 响应式数据变更导致DOM更新后调用 |
| `onUnmounted()` | `unmounted` | 组件卸载时调用，用于清理定时器、取消订阅 |
| `onBeforeMount()` | `beforeMount` | 挂载开始前调用 |

### 2.2 Vite 6.x

Vite作为新一代前端构建工具，利用浏览器原生ES Module支持，在开发阶段提供极速的模块热替换（HMR），在生产构建阶段基于Rollup实现高效的代码优化。

**开发服务器（HMR）：**

Vite的开发服务器不进行全量打包，而是按需编译。当修改某个组件时，Vite仅需重新编译该组件及其依赖链，HMR更新速度与项目规模无关，始终保持毫秒级响应。

**生产构建优化：**

| 优化策略 | 说明 |
|---------|------|
| 代码分割（Code Splitting） | 基于动态`import()`实现路由级代码分割，每个页面独立打包，按需加载 |
| Tree-shaking | 基于ES Module静态分析，移除未引用的代码，显著减小包体积 |
| 路由懒加载 | 配合`webpackChunkName`魔法注释，为异步chunk指定语义化名称，便于调试和预加载 |

```javascript
{
  path: '/items/:id',
  component: () => import(/* webpackChunkName: "item-detail" */ '@/views/portal/ItemDetail.vue')
}
```

### 2.4 Pinia 2.2.x

Pinia是Vue 3官方推荐的状态管理库，替代Vuex成为新一代状态管理方案。本系统使用Pinia管理全局状态，特别是认证相关的核心状态。

**核心Store设计——auth store：**

```javascript
export const useAuthStore = defineStore('auth', () => {
  const token = ref(null)
  const user = ref(null)
  const roles = ref([])

  function isAuthenticated() {
    return !!token.value
  }

  function hasRole(role) {
    return roles.value.includes(role)
  }

  async function login(credentials) {
    const res = await authApi.login(credentials)
    token.value = res.data.token
    user.value = res.data.user
    roles.value = res.data.roles
  }

  function logout() {
    token.value = null
    user.value = null
    roles.value = []
  }

  return { token, user, roles, isAuthenticated, hasRole, login, logout }
})
```

**Hydrate机制（localStorage持久化）：**

Pinia本身不提供状态持久化能力，本系统通过hydrate机制实现Token等关键状态的localStorage持久化，确保页面刷新后认证状态不丢失：

- **写入时机**：登录成功后，将Token、用户信息、角色列表序列化写入localStorage
- **读取时机**：应用初始化时，从localStorage读取并恢复auth store状态
- **清除时机**：登出操作或Token过期时，清除localStorage中的对应键值

```javascript
router.beforeEach((to, from, next) => {
  const authStore = useAuthStore()

  if (!authStore.isAuthenticated() && to.path !== '/login') {
    next('/login')
    return
  }

  if (to.meta.roles && !to.meta.roles.some(r => authStore.roles.includes(r))) {
    next('/403')
    return
  }

  next()
})
```

### 2.6 Tiptap 3.x

Tiptap是基于ProseMirror的无头（Headless）富文本编辑器框架，本系统使用其构建商品描述的富文本编辑功能。

**扩展配置：**

| 扩展名称 | 功能说明 |
|---------|---------|
| starter-kit | 基础编辑功能集合（段落、标题、加粗、斜体、列表等） |
| image | 图片插入与展示 |
| link | 超链接插入 |
| placeholder | 占位符提示（如"请输入商品描述..."） |

**v-model双向绑定：**

Tiptap编辑器通过v-model与Vue组件状态实现双向绑定，编辑器内容变化自动同步至组件变量，外部赋值也自动反映到编辑器视图：

```vue
<template>
  <EditorContent :editor="editor" />
</template>

<script setup>
import { useEditor, EditorContent } from '@tiptap/vue-3'
import StarterKit from '@tiptap/starter-kit'
import Image from '@tiptap/extension-image'
import Link from '@tiptap/extension-link'
import Placeholder from '@tiptap/extension-placeholder'

const editor = useEditor({
  content: modelValue.value,
  extensions: [StarterKit, Image, Link, Placeholder.configure({ placeholder: '请输入商品描述...' })],
  onUpdate: ({ editor }) => {
    emit('update:modelValue', editor.getHTML())
  }
})
</script>
```

### 2.7 ECharts 6.x + vue-echarts

ECharts是百度开源的数据可视化库，本系统在运营后台中广泛使用其进行数据统计展示，并通过vue-echarts组件实现与Vue 3的深度集成。

**图表类型与应用场景：**

### 3.3 Spring Security

Spring Security是本系统的安全框架，负责认证（Authentication）和授权（Authorization）两大核心安全功能。

**SecurityFilterChain配置：**

Spring Security 6.x采用组件化配置方式，通过`SecurityFilterChain` Bean替代传统的XML配置和WebSecurityConfigurerAdapter：

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .cors(cors -> cors.configurationSource(corsConfigurationSource()))
        .sessionManagement(session ->
            session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/api/ops/**").hasRole("OPS")
            .requestMatchers("/api/items", "/api/items/{id}").permitAll()
            .anyRequest().authenticated())
        .addFilterBefore(jwtAuthenticationFilter(),
            UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
```

**JwtAuthenticationFilter：**

自定义JWT认证过滤器继承`OncePerRequestFilter`，确保每个请求仅执行一次过滤逻辑：

```java
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {
        String token = jwtUtil.extractToken(request);
        if (token != null && jwtUtil.validateToken(token)) {
            String username = jwtUtil.extractUsername(token);
            Long userId = jwtUtil.extractUserId(token);
            List<String> roles = jwtUtil.extractRoles(token);

            UsernamePasswordAuthenticationToken authentication =
                new UsernamePasswordAuthenticationToken(
                    username, null,
                    roles.stream().map(r ->
                        new SimpleGrantedAuthority("ROLE_" + r)).toList());

            SecurityContextHolder.getContext().setAuthentication(authentication);
        }
        filterChain.doFilter(request, response);
    }
}
```

**@EnableMethodSecurity方法级权限：**

通过`@EnableMethodSecurity`注解启用方法级安全控制，允许在Service方法上使用`@PreAuthorize`注解声明细粒度权限：

```java
@PreAuthorize("hasRole('OPS')")
public ReviewResult reviewItem(Long itemId, ReviewDecision decision) { ... }

@PreAuthorize("hasAnyRole('BUYER', 'SELLER')")
public OrderDTO createOrder(OrderCreateDTO dto) { ... }
```

**BCryptPasswordEncoder密码编码：**

系统使用Spring Security内置的BCryptPasswordEncoder进行密码加密，BCrypt算法具有以下安全特性：

- **自动加盐**：每次加密自动生成随机盐值，相同明文产生不同密文
- **不可逆加密**：单向哈希，无法从密文反推明文
- **可调成本因子**：通过增加计算轮数抵御暴力破解

### 3.4 JdbcTemplate数据访问

本系统在技术选型上，虽然引入了Spring Data JPA依赖，但实际数据访问层采用JdbcTemplate进行直接SQL操作。

**技术选型理由：**

| 对比维度 | JPA/Hibernate | JdbcTemplate |
|---------|--------------|-------------|
| SQL控制 | 框架自动生成，复杂查询需HQL/Criteria | 完全手写SQL，精确控制查询逻辑 |
| 学习曲线 | 需理解实体映射、懒加载、N+1问题 | 只需掌握SQL和Spring JDBC API |
| 性能调优 | 需理解Hibernate内部机制 | SQL透明，调优直观 |
| 复杂查询 | 多表关联查询表达复杂 | 原生SQL，灵活高效 |
| 返回类型 | 强类型实体 | Map\<String, Object\>灵活返回 |

**核心数据访问模式：**

```java
@Repository
public class ItemRepositoryImpl implements ItemRepository {

    private final JdbcTemplate jdbcTemplate;

    @Override
    public Map<String, Object> findById(Long id) {
        String sql = "SELECT * FROM item WHERE id = ?";
        return jdbcTemplate.queryForMap(sql, id);
    }

    @Override
    public Page<Map<String, Object>> findBySellerId(Long sellerId, int page, int size) {
        String countSql = "SELECT COUNT(*) FROM item WHERE seller_id = ?";
        Integer total = jdbcTemplate.queryForObject(countSql, Integer.class, sellerId);

        String querySql = "SELECT * FROM item WHERE seller_id = ? ORDER BY created_at DESC LIMIT ? OFFSET ?";
        List<Map<String, Object>> items = jdbcTemplate.queryForList(
            querySql, sellerId, size, page * size);

        return new PageImpl<>(items, PageRequest.of(page, size), total);
    }
}
```

**手动分页实现：**

由于使用JdbcTemplate，分页逻辑需要手动实现。系统采用`LIMIT ? OFFSET ?`模式，配合COUNT查询获取总记录数，封装为Spring Data的Page对象，保持与前端分页组件的兼容性。

### 3.6 JJWT 0.12.6

JJWT（Java JWT）是本系统用于JWT Token生成和解析的库。

**Token生成：**

```java
public String generateToken(String username, Long userId, List<String> roles) {
    return Jwts.builder()
        .subject(username)
        .claim("userId", userId)
        .claim("roles", roles)
        .issuedAt(new Date())
        .expiration(new Date(System.currentTimeMillis() + 86400000))
        .signWith(secretKey)
        .compact();
}
```

**Token解析与验证：**

```java
public Claims parseToken(String token) {
    return Jwts.parser()
        .verifyWith(secretKey)
        .build()
        .parseSignedClaims(token)
        .getPayload();
}
```

**安全特性：**

| 特性 | 说明 |
|------|------|
| HMAC-SHA签名 | 使用对称密钥签名，确保Token未被篡改 |
| Claims解析 | 从Payload中提取标准声明（sub、iat、exp）和自定义声明（userId、roles） |
| 过期检测 | 解析时自动校验exp字段，过期Token抛出ExpiredJwtException |
| 24小时有效期 | Token有效期为24小时（86400000ms），平衡安全性与用户体验 |

### 3.7 GlobalExceptionHandler

统一异常处理器通过`@RestControllerAdvice`注解实现全局异常拦截，将各类异常转换为统一的API响应格式：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleException(Exception e) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(ApiResponse.error(500, "服务器内部错误"));
    }

    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<ApiResponse<Void>> handleAccessDenied(AccessDeniedException e) {
        return ResponseEntity.status(HttpStatus.FORBIDDEN)
            .body(ApiResponse.error(403, "权限不足"));
    }

    @ExceptionHandler(RuntimeException.class)
    public ResponseEntity<ApiResponse<Void>> handleRuntime(RuntimeException e) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(ApiResponse.error(400, e.getMessage()));
    }
}
```

**异常处理策略：**

| 异常类型 | HTTP状态码 | 业务码 | 说明 |
|---------|-----------|--------|------|
| AccessDeniedException | 403 | 403 | 权限不足，无权访问该资源 |
| ExpiredJwtException | 401 | 401 | Token已过期，需重新登录 |
| RuntimeException | 400 | 400 | 业务逻辑异常，返回具体错误信息 |
| Exception | 500 | 500 | 未预期的系统异常，返回通用错误提示 |

### 4.2 索引策略

合理的索引设计是数据库性能优化的关键。本系统针对不同查询场景设计了四类索引：

**单列索引——外键字段与高频查询字段：**

针对外键关联查询和高频过滤字段建立单列索引，加速WHERE条件过滤和JOIN关联：

```sql
CREATE INDEX idx_item_seller_id ON item(seller_id);
CREATE INDEX idx_item_status ON item(status);
CREATE INDEX idx_orders_buyer_id ON orders(buyer_id);
CREATE INDEX idx_orders_seller_id ON orders(seller_id);
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_favorite_user_id ON favorite(user_id);
CREATE INDEX idx_message_receiver_id ON message(receiver_id);
CREATE INDEX idx_notification_user_id ON notification(user_id);
```

**联合索引——复合查询场景：**

针对多字段组合查询场景建立联合索引，遵循最左前缀匹配原则：

```sql
CREATE INDEX idx_item_seller_review ON item(seller_id, review_status);
CREATE INDEX idx_item_status_created ON item(status, created_at);
CREATE INDEX idx_address_user_default ON address(user_id, is_default);
CREATE INDEX idx_orders_buyer_status ON orders(buyer_id, status);
```

**唯一索引——业务唯一约束：**

通过唯一索引保证业务层面的数据唯一性，防止重复数据插入：

```sql
CREATE UNIQUE INDEX uk_user_username ON user_account(username);
CREATE UNIQUE INDEX uk_ops_username ON ops_account(username);
CREATE UNIQUE INDEX uk_favorite_user_item ON favorite(user_id, item_id);
CREATE UNIQUE INDEX uk_circle_like_post_user ON circle_like(post_id, user_id);
CREATE UNIQUE INDEX uk_orders_order_no ON orders(order_no);
```

**排序索引——DESC排序场景：**

针对高频的降序排序场景，建立降序索引以避免filesort：

```sql
CREATE INDEX idx_item_hot_score ON item_stats(hot_score DESC);
CREATE INDEX idx_item_view_count ON item_stats(view_count DESC);
CREATE INDEX idx_item_click_count ON item_stats(click_count DESC);
CREATE INDEX idx_item_created_at ON item(created_at DESC);
```

### 4.3 字符集与排序规则

本系统统一采用`utf8mb4`字符集和`utf8mb4_unicode_ci`排序规则：

| 配置项 | 值 | 说明 |
|-------|-----|------|
| 字符集 | utf8mb4 | MySQL中真正的UTF-8编码，每个字符最多4字节，完整支持Unicode |
| 排序规则 | utf8mb4_unicode_ci | 基于Unicode标准的排序规则，不区分大小写，支持多语言排序 |

**选择utf8mb4而非utf8的原因：**

MySQL中的`utf8`字符集实际上是`utf8mb3`，每个字符最多3字节，不支持4字节的Unicode字符（如emoji表情、部分生僻汉字）。`utf8mb4`才是真正的UTF-8编码，对于校园二手交易平台而言，用户在商品描述、评价、圈子帖子中广泛使用emoji表情，必须使用`utf8mb4`才能正确存储和展示。

### 4.4 审计字段设计

所有业务表均包含`created_at`和`updated_at`两个审计字段，用于记录数据的创建时间和最后修改时间：

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

| 字段 | 默认值 | 更新策略 | 说明 |
|------|--------|---------|------|
| created_at | CURRENT_TIMESTAMP | 插入时自动设置 | 记录数据创建时间，后续不变 |
| updated_at | CURRENT_TIMESTAMP | 插入时设置，更新时自动刷新 | 记录数据最后修改时间 |

审计字段的应用场景包括：按时间排序展示商品列表、计算订单超时、统计交易趋势、数据变更追溯等。

## 5 安全机制

### 5.1 JWT认证流程

JWT认证是本系统安全体系的核心，实现了从用户登录到请求鉴权的完整认证链路。

**完整认证流程：**

```
┌─────────┐                                                  ┌──────────────┐
│         │  ① POST /api/auth/login                          │              │
│         │  { username, password }                          │              │
│  前端    │ ──────────────────────────────────────────────→ │  Controller  │
│  应用    │                                                  │              │
│         │  ④ { code:200, data: { token, user, roles } }    │              │
│         │ ←────────────────────────────────────────────── │              │
└────┬────┘                                                  └──────┬───────┘
     │                                                              │
     │ ⑤ 存储Token至localStorage                                    │ ② 调用Service
     │    存储user/roles至Pinia store                               │    验证用户名密码
     │                                                              │
     │                                                              │ ③ 密码匹配则
     │                                                              │    JwtUtil.generateToken()
     │                                                              │    生成JWT
     ▼                                                              ▼
┌─────────┐                                                  ┌──────────────┐
│         │  ⑥ GET /api/items                                │              │
│         │  Authorization: Bearer eyJhbG...                  │  JwtAuth     │
│  前端    │ ──────────────────────────────────────────────→ │  Filter      │
│  应用    │                                                  │              │
│         │  ⑨ { code:200, data: [...] }                     │  ⑦ 解析Token │
│         │ ←────────────────────────────────────────────── │  ⑧ 设置认证  │
└─────────┘                                                  └──────────────┘
```

**流程步骤详解：**

1. **登录请求**：用户在前端输入用户名和密码，前端通过Axios发送POST请求至登录接口
2. **密码验证**：Controller层调用Service层，Service层通过BCryptPasswordEncoder比对密码哈希
3. **Token生成**：密码验证通过后，JwtUtil生成JWT Token，Payload包含username、userId、roles、iat、exp
4. **返回Token**：将Token、用户信息、角色列表封装为统一响应格式返回前端
5. **前端存储**：前端将Token存入localStorage，用户信息和角色列表存入Pinia auth store
6. **请求携带Token**：后续请求通过Axios请求拦截器自动在Header中注入`Authorization: Bearer <Token>`
7. **Token解析**：JwtAuthenticationFilter从Header中提取Token，调用JwtUtil解析Claims
8. **设置认证**：将解析出的用户名和角色构造为UsernamePasswordAuthenticationToken，设置到SecurityContext
9. **业务处理**：请求通过认证后进入Controller和Service层正常处理业务逻辑

### 5.2 BCrypt密码加密

本系统采用BCrypt算法进行密码加密存储，BCrypt是基于Blowfish密码算法的自适应哈希函数。

**BCrypt安全特性：**

| 特性 | 说明 |
|------|------|
| 自动加盐 | 每次加密自动生成128位随机盐值，嵌入密文中，无需单独存储盐值 |
| 不可逆 | 单向哈希函数，无法从密文反推明文，只能通过明文重新计算进行验证 |
| 可调成本 | 默认成本因子为10（2^10=1024轮），可增大成本因子抵御算力增长 |
| 密文格式 | `$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy` |

**密文格式解析：**

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │  │  │                      │
 │  │  │                      └── 哈希值（31字符）
 │  │  └── 盐值（22字符）
 │  └── 成本因子（10 = 2^10轮）
 └── 算法版本
```

### 5.3 CORS配置

跨域资源共享（CORS）配置允许前端SPA应用跨域访问后端API。

**当前配置：**

```java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration configuration = new CorsConfiguration();
    configuration.addAllowedOriginPattern("*");
    configuration.setAllowCredentials(true);
    configuration.addAllowedHeader("*");
    configuration.addAllowedMethod("*");

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", configuration);
    return source;
}
```

| 配置项 | 值 | 说明 |
|-------|-----|------|
| allowedOriginPattern | * | 允许所有来源的跨域请求 |
| allowCredentials | true | 允许携带Cookie和Authorization Header |
| allowedHeader | * | 允许所有请求头 |
| allowedMethod | * | 允许所有HTTP方法（GET/POST/PUT/DELETE等） |

> **注意**：当前配置为开发环境便利性设置为允许所有来源。生产环境应将`addAllowedOriginPattern("*")`替换为具体的前端域名，如`addAllowedOrigin("https://campus-market.example.com")`，以降低跨域攻击风险。

### 5.4 CSRF防护

跨站请求伪造（CSRF）是一种利用已认证用户的身份发起恶意请求的攻击方式。

**本系统禁用CSRF防护的理由：**

1. **JWT无状态认证**：本系统使用JWT Token进行身份验证，Token存储在localStorage中，而非Cookie。CSRF攻击的核心前提是浏览器自动携带Cookie，而localStorage中的Token不会被浏览器自动携带
2. **手动注入Token**：每次请求需要通过Axios拦截器手动在Authorization Header中注入Token，攻击者无法通过恶意页面触发自动携带
3. **CORS限制**：跨域请求受CORS策略限制，攻击者的恶意页面无法读取响应内容

```java
http.csrf(csrf -> csrf.disable())
```

### 5.5 接口权限控制

本系统实现了三层接口权限控制，从粗粒度到细粒度逐层收窄权限范围：

**URL级权限——SecurityConfig配置：**

在Spring Security的SecurityFilterChain中，通过URL模式匹配定义接口级别的访问规则：

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/**").permitAll()         // 认证接口公开访问
    .requestMatchers("/api/items", "/api/items/{id}").permitAll()  // 商品浏览公开
    .requestMatchers("/api/ops/**").hasRole("OPS")       // 运营接口需OPS角色
    .requestMatchers("/api/cart/**").authenticated()      // 购物车需登录
    .requestMatchers("/api/orders/**").authenticated()    // 订单需登录
    .anyRequest().authenticated()                         // 其余接口需登录
)
```

**角色级权限——路由守卫校验：**

前端路由通过meta.roles声明所需角色，全局路由守卫在导航前校验用户角色：

```javascript
// 路由配置
{ path: '/ops/dashboard', meta: { roles: ['OPS'] } }
{ path: '/seller/items',  meta: { roles: ['SELLER'] } }

// 路由守卫
router.beforeEach((to, from, next) => {
  const authStore = useAuthStore()
  if (to.meta.roles && !to.meta.roles.some(r => authStore.roles.includes(r))) {
    next('/403')
  } else {
    next()
  }
})
```

**方法级权限——@PreAuthorize注解：**

在Service方法上使用`@PreAuthorize`注解声明细粒度权限，支持SpEL表达式实现复杂权限逻辑：

```java
@PreAuthorize("hasRole('OPS')")
public ReviewResult reviewItem(Long itemId, ReviewDecision decision) { ... }

@PreAuthorize("hasAnyRole('BUYER', 'SELLER')")
public OrderDTO createOrder(OrderCreateDTO dto) { ... }

@PreAuthorize("hasRole('SELLER') and #item.sellerId == authentication.principal.userId")
public void updateItem(Item item) { ... }
```

### 5.6 Token安全机制

**Token生命周期管理：**

| 环节 | 策略 | 说明 |
|------|------|------|
| Token生成 | HMAC-SHA签名 | 使用服务端密钥签名，确保Token未被篡改 |
| Token有效期 | 24小时 | 平衡安全性与用户体验，避免频繁登录 |
| Token存储 | localStorage | 前端持久化存储，页面刷新后Token不丢失 |
| Token携带 | Authorization Header | 每次请求通过Header携带，不使用Cookie |
| Token过期检测 | isJWTExpired工具函数 | 前端在发起请求前检测Token是否过期，避免无效请求 |
| Token失效处理 | 401自动清除 | 响应拦截器捕获401状态码，自动清除Token并跳转登录页 |

**前端Token过期检测：**

```javascript
export function isJWTExpired(token) {
  if (!token) return true
  try {
    const payload = JSON.parse(atob(token.split('.')[1]))
    return payload.exp * 1000 < Date.now()
  } catch {
    return true
  }
}
```

**401自动处理流程：**

```
请求发送 → 后端验证Token → Token无效/过期 → 返回401
                                              │
前端响应拦截器捕获401 ←────────────────────────┘
         │
         ▼
清除localStorage中的Token
清除Pinia auth store状态
跳转至登录页面
```
